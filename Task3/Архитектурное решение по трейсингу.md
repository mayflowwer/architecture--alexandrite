# Контекст
После запуска публичного API для приема и обработки заказов сторонных клиентов была выявлена проблема потери заказов.
Заказы создаются, однако в процессе работы теряются и не попадают к исполнителям. На текущий момент не известна на каком шаге коммуникации систем происходит разрыв или ошибка.
Бизнес-процесс создания и изменения статуса заказа доступен [здесь](./order_state_diagram.puml).
Для диагностики и локализации проблемы до уровня сервиса или сервисной коммуникации требуется отслеживать цепочки коммуникаций.

# Мотивация
Остлеживание цепочек взаимодействия сервисов предлагается внедрять с помощью трейсинга вызовов:
- связать все события жизненного цикла заказа в единую цепочку через `trace_id`, уникальный идентификатор, который будет генерироваться в контексте Shop API и характеризовать конкретный id ордера клиента
- локализовать сервис или шаг коммуникации, на котором происходит потеря
- сократить время диагностики инцидентов за счёт визуализации цепочки вызовов
- в дальнейшем использовать трассировку как основу для мониторинга производительности отдельных этапов обработки заказа

Собираемые метрики:
1. Количество уникальных trace_id с span_id сервисов;
2. Количество trace_id с нефинальным статусом - кол-во проблемных заказов;
3. Время смены статусов заказа - время между span_id;
4. Количество span-ов с ошибками по сервисам — где чаще всего происходят сбои

Влияние на бизнес-метрики:
1. Уменьшение времени диагностики проблемы потери ордера за счет четкой локализации проблемы (span_id покажет на каком шаге возникла проблема коммуникации систем)
2. Уменьшение времени обработки заказа за счет понимания, на каком шаге операция производится медленно или неэффктивно. 

# Предлагаемое решение
Шаг 1. Внедрение сервиса Jaeger а IT-ландшафт компании:
1) Для отслеживания трейсинга предлагается поднять сервис Jaeger для сбора трейсинга и Jaeger-UI для визуализации и поиска в web-интерфейсе.

Шаг 2. Доработка на стороне API-сервисов
1) Требуется добавить модуль Jaeger в кодовую базу API-сервисов
2) Добавить логику генерации уникального span_id (идентификатора подзапроса сервиса-участника флоу) в эндпоинты изменения статуса ордера, передачу сообщения в HTTP-заголовке следующему участнику цепочки и отправку сообщения в сервис Jaeger. Список сервисов и данные сообщения для добавления доступны на [схеме](./order_state_diagram_tracing.puml)
3) Целевая схема контейнеров IT-ландшафта доступна [здесь].

# Компромиссы
Внедрение трейсинга - дополнительная задача небизнесового характера на команду API-сервисов. Требуется согласовать план внедрения трейсинга в критично важные этапы жизни ордера, например:
- переход в статус SUBMITTED в контексте сервиса Shop API;
- переход в статус PRICE_CALCULATED в контексте сервиса Mes API;
- переход в статус MANUFACTURING_STARTED в контексте сервиса Mes API;
- переход в статус SHIPPED в контексте сервиса Mes API.

Также требуется определить и согласовать TTL хранения трейсинг-данных, после которого данные будут удаляться и не будет возможности проводить диагностику инцидентов. Требуется согласование реглаемента доступа и использования трейсинг-данных в процессе работы с тикетами клиентов.

В рамках обеспечения ИБ требуется ограничить доступ к данным сервиса Jaeger до devOps-инженеров и девеоперов, доступ закрыть за авторизацией.

# Контекст
После подключения компанией внешнего API клиенты стали жаловаться на потерю заказов. Флоу работы с заказами предполагает участие нескольких сервисов, нет возможности локализовать область и определить точку некорретной работы. Сейчас из-за невозможности диагностики клиентам потерянных заказов связываются персонально и предоставляют доп. скидки.
Компания несет финансовые убытки из-за недополучения прибыли клиентов, а ресурс менеджеров тратится на ненужную работу. It-команда, обеспечивающая работоспособность сервисов, не обладает знаниями о настоящих причинах проблемы и вынуждена реактивно перезагружать сервера сервисов.

# Мотивация
Для возможности превентивного реагирования на проблемы необходимо внедрение подхода "наблюдаемости" системы, а именно мониторинга.
Мониторинг позволит:
- видеть состояние системы в реальном времени, иметь возможность превентивено реагироваь и устранять проблему перегрузки вычислительных мощностей до наступления финансовых убытков;
- снизить недовольство клиентов (как внутренних, так и внешних), связанное с некоректной работой системы, повысить общую удовлетворенность сервисом, работать на клиентоориентированость и репутацию компании;
- дифференцировать нормальное поведение системы от аномального;
- оценивать загруженность компонентов системы, планировать работы по обслуживанию и ремонту компонентов;
- количественно оценивать необходимость технических изменений там, где есть проблемы технического характера, не растрачиваем ресурсы it-команды на ненужную работу, экономить ресурс разработчиков и devOps-инженеров.

# Выбор подхода к мониторингу
Для повышения наблюдаемости требуется определить метрики, которые мы хотим собирать для оценки состояния системы. Предлагается собирать следующие метрики:
1. Mes API:
  - контекст расчета стоимости изделия:
    1. время загрузки файла 3d-модели в RAM сервера по 95-му перцентилю
    2. время расчета стоимости изделия по 95-му перцентилю
    3. количество обработанных сообщений из Rabbit MQ в 1 ед. времени
    4. сатурация - количество задач расчета стоимости изделий в очереди (в топике Rabbit MQ ), кот Mes API не может обработать 
  - контекст маппинга заказов на исполнителей:
    1. время ассайна исполнителя на ордер по 95-му перцентилю
  - отображение списка ордеров исполнителям в web-интерфейсе:
    1. время получения списка ордеров для выдачи web-странице
    2. количество запросов к backend-серверу для выдачи списка ордеров (RPS)
  - дополнительно:
    1. количество http-запросов, поступающих напрамую в Mes API, без брокера сообщений (через External Orders API)
    2. количество ошибок (4xx, 5xx коды)
    3. % загрузки процессора (CPU usage)
    4. утилизация RAM
    5. healthcheck — доступность сервиса (true/false)
2. Mes DB:
  - количество запросов к базе данных Mes для подбора списка ордеров (QPS), запись 
  - количество открытых коннекшенов / всего коннекшенов
  - время обработки запроса на чтение данных по 95-му перцентилю
  - время обработки запроса на запись данных по 95-му перцентилю
  - количество ошибок при выполнении запросов
  - healthcheck — доступность базы данных (true/false)
3. CRM API:
  - количество обработанных сообщений из Rabbit MQ в 1 ед. времени
  - сатурация - количество сообщений от Mes API (в топике Rabbit MQ ): изменение статусов ордеров, одеры, по кот. посчиталась стоимость, и проч.
  - % загрузки процессора (CPU usage)
  - утилизация RAM
  - количество ошибок при обработке сообщений
  - healthcheck
4. Shop API:
  - контекст обработки запросов от web-клиентов:
    1. количество http-запросов от клиента (с разграничением на тип запросов) в 1 ед. времени (RPS)
    2. время обработки одного http-запроса по 95-му перцентилю
    3. % загрузки процессора (CPU usage)
    4. утилизация RAM
    5. количество ошибок (4xx, 5xx коды)
    6. healthcheck — доступность сервиса
5. Shop DB:
  - количество запросов к базе данных (QPS) на операции чтения и записи
  - количество открытых коннекшенов / всего коннекшенов
  - время обработки запроса на чтение данных по 95-му перцентилю
  - время обработки запроса на запись данных по 95-му перцентилю
  - количество ошибок при выполнении запросов
  - healthcheck — доступность базы данных
6. Rabbit MQ:
   - топик orders.calculateAmount: 
    1. количество dead-letter 
    2. количество сообщений in-flight от CRM API и от Mes API
    3. глубина очереди (queue depth) — количество сообщений, ожидающих обработки
    4. consumer lag — отставание воркера от producer
   - топик orders.approving:
    1. queue depth
    2. количество dead-letter
    3. consumer lag
    4. количество сообщений in-flight
7. Internet Shop:
   1. длительность ответа после создания заявки ордера в интернет-магазине
   2. количество ошибок на клиенте (JS errors)
   3. RPS на создание заказов

Контексты, в рамках которых клиент напрямую взаимодействует с системой, предлагается оценивать по методу RED (например, взаимодействие сервисов Internet Shop, Shop API, Shop DB).
Основные вычислительные компоненты всех сервисов предлагается оценивать по модели USE. 

# План действий
Сбор показателей и их агрегацию предлагается реаизовывать через внедрение инструмента Prometheus.
Этап 1.
Необходимо:
1. Поднять сервер HTTP-сервер для обработки запросов с time-series db 
2. Мониторинг API-сервисов:
   1. Включить соответствующую библиотеку сбора данных в кодовую базу API-сервисов:
      1. для сервисов Shop API, CRM API - micrometer-registry-prometheus для Spring Boot
      2. для сервиса Mes API - prometheus-net 
   2. Проверить работоспособность эндпоинта /metrics, который агент Prometheus будет опрашивать и получать показатели
   3. Согласовать и открыть порт api-сервиса, чтобы  агент Prometheus смог делать запрос 
3. Мониторинг баз данных Shop DB, Mes DB:
   1. Создать УЗ пользователя клиента Prometheus для подключения и получения данных системынх таблиц
   2. Запустить на серверах баз данных postgres_exporter с выданной УЗ
4. Мониторинг брокера сообщений:
   1. Включить плагин rabbitmq_prometheus на сервере брокера
5. Настроить prometheus.yml, прописать все таргеты
6. Просматривать метрики в web-клиенте Prometheus
